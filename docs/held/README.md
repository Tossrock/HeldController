# Held — LED controller

Firmware and control UI for **Held**, a ~750 × 500 mm 3D-printed anatomical heart. Six "missing pieces" hang from chains; pushing them back in triggers hall sensors, and the LEDs inside respond. This fork of WLED keeps WLED's WiFi setup, LED hardware configuration and web server, and adds:

- a **layered pattern engine** (base layers plus timed events, alpha-composited) that runs as a WLED effect,
- a **phone-friendly control UI** with a 3D simulator, served by the controller at `/`,
- a **JSON control API** for the sensors and the audio board.

## Quick start

### Run the UI without hardware

Use either of these:

- Open `wled00/data/held/index.htm` directly in a browser (double-click it).
- Run `npm run held:sim` and browse to http://localhost:8080.

With no controller answering, the page runs as a **simulator**: the full pattern engine runs in the browser, and settings are kept in browser storage. To drive a real controller from your laptop, use either of these:

- `npm run held:sim -- --device 192.168.1.50` proxies the API to the controller.
- Enter the controller's address in **Setup → Connection**.

### Build and flash

```bash
npm ci
npm run build                 # builds the web UI headers (also run automatically by PlatformIO)
pio run -e held_esp32         # firmware
pio run -e held_esp32 -t upload
```

> On Windows, run `pio` from **PowerShell or cmd, not Git Bash**. The ESP-IDF tool installer refuses MSYS shells ("MSys/Mingw is not supported"), which leaves an empty toolchain and later fails with `xtensa-esp32-elf-g++ is not recognized`.

### First boot

1. The controller opens a WiFi access point **`Held-AP`** (password `heldgently`).
2. Join it. The captive portal opens the Held UI directly. To join another WiFi network instead, use **Setup → links → WiFi** (`/settings/wifi`).
3. In **Strip config → Hardware**, set each LED output's type (e.g. WS281x, or APA102 with a clock pin), data pin, LED count and color order, then press **Apply LED outputs**. **Each LED output becomes one Held strip** (the `held_esp32` build enables WLED auto-segments: one segment per output). The audio link pins are set in the same section. See [Hardware configuration](#hardware-configuration).
4. Open the controller's address (or `http://held.local`) for the Held UI. The stock WLED UI is still available at `/classic` for diagnostics.

## How the engine works

Every frame, each strip is rendered into a float RGB buffer by compositing these layers in order:

| Layer | Kind | What it does |
|---|---|---|
| `heartbeat` | base | Lub-dub waveform (or ECG / single bump) emitted from the strip's **origin** at the BPM, travelling outward to the antipode. Brightness varies above *and below* the baseline. |
| `ambient` | base | Slow periodic gradient noise (wraps seamlessly around the ring, and drifts along the strip at `noisePan` LED/s) plus twinkles that rise, shimmer and fall. |
| `pieceIn` | event | A fast pulse train of decreasing magnitude spreading from the origin. |
| `pieceOut` | event | The scene dims and falters with sudden high-frequency V flicker bursts. |
| `allIn` | event | White sparkles, then crossing pulses that speed up and flicker-merge into a solid colour. The colour holds, then decays in reversed heartbeats back to the base state. |

**Level.** The piece count sets a target level of `min(pieces, numPieces-1) / (numPieces-1)`, so it is 0 with no pieces in and 1 with five of six. The engine eases toward it with `levelSmoothing`. Any numeric parameter can be **ranged**, written as `[valueAtLevel0, valueAtLevel1]`, and then follows the level. In the UI, the ⇆ button splits a slider into "0 pcs" and "5 pcs" values. Heart rate, pulse speed and baseline brightness are ranged by default.

**Events** fire automatically when the piece count changes (`autoEvents`):

| Change | Event |
|---|---|
| Count goes up | `pieceIn` |
| Count reaches all pieces | `allIn` (instead of `pieceIn`). If an `allIn` is already playing, it is not restarted. |
| Count goes down | `pieceOut`; if it dropped from all pieces, the running `allIn` fades out over `cancelFade` |
| Count goes down during the last `releaseGrace` seconds of `allIn` (default 10 s) | Nothing: no `pieceOut`, and `allIn` keeps playing. The level still follows the count. |

Events can also be triggered by hand, from the UI or the API.

**Expressions.** Any numeric layer parameter can instead be a small program, written in JavaScript syntax, that is evaluated every frame. In the UI, the ƒ button turns a slider into an editor pre-filled with the current value or `lerp(start, end, level)`, for example:

```js
(pieces, t, et, level) => 0.4 + 0.2 * wave(t / 4)          // breathe every 4 s
(pieces, t) => { let base = lerp(45, 70, pieces / 5); return base + 3 * sin(t); }
(p, t, et) => 4 + 6 * et                                     // on an event layer: grows as the event plays
```

- **Inputs:** `pieces` (count held), `t` (engine seconds), `et` (event age in seconds; 0 on base layers), `level` (smoothed 0..1) and `numPieces`. Header names are optional and bind positionally, so `(n, time) =>` works.
- **Language:** `+ - * / % **`, comparisons, `&& || !`, `?:`, and `{ let …; return …; }` blocks.
- **Functions:** `sin cos tan asin acos atan atan2 sqrt abs floor ceil round trunc sign exp log pow min max fract mod clamp lerp smoothstep wave triangle square noise rnd` (`Math.` prefixes are accepted), plus the constants `PI TAU E`.
- **Results** are clamped to the parameter's range.

This is not full JavaScript: there are no loops and no other functions. The firmware compiles the same language to bytecode (`wled00/held/held_expr.cpp`, mirrored by `wled00/data/held/expr.js`), so whatever the simulator accepts runs identically on the controller. Global and strip settings can't be expressions, and at most 24 parameters can hold one at a time.

**Strip geometry.** These per-strip settings are shared by every layer, so events originate from the same point as the heartbeat:

- `origin` (the offset)
- `reps` (repetitions)
- `mirror` (whether alternate repetitions are mirrored or repeated)

With repetitions, the whole composited pattern (every layer and event) is rendered into `leds/reps` pixels with the origin at its start. Copies of it are then tiled around the strip from the origin, and with `mirror` every other copy runs backwards. Pulses travel within one copy, so `travel` 0.5 meets in the middle of each copy. Pulses wrap across the physical ends of a strip. Strips can have different lengths and origins. Up to 4 strips are supported.

**Colour.** Values are perceptual (gamma-normalised) 0..1; WLED's gamma correction maps them to PWM. Global brightness is WLED's `bri`.

## Control API (sensors, audio board)

Send a **held command object** in any of these ways:

| Transport | How |
|---|---|
| HTTP | `POST /json/held` with the object as the body. The reply is the current held state. |
| WebSocket / WLED JSON | Wrap it as `{"held": {...}}` and send it to `/ws` or `POST /json/state`. |
| Serial | WLED's serial JSON API at 115200 baud: send `{"held": {...}}` followed by a newline. |

| Key | Example | Effect |
|---|---|---|
| `mask` | `{"mask": 13}` | Which pieces are in (bit *n* = piece *n+1*). Fires events per the rules above. |
| `pieces` | `{"pieces": 3}` | Same, as a count (fills the lowest bits). |
| `trigger` | `{"trigger": "allIn"}` | Play `pieceIn`, `pieceOut`, `allIn` or `storyEnd` (a string or an array). |
| `link` | `{"link": "COUNT 3 6"}` | Handle a line (or array of lines) exactly as if it came from the audio board. For testing without it. |
| `cancel` / `clear` | `{"clear": true}` | Fade out an event type / drop all events. |
| `params` | `{"params": {"heartbeat": {"bpm": [40, 80]}}}` | Partial parameter update. Colours are `"#RRGGBB"` or numbers. A string on a numeric parameter is an expression, e.g. `"bpm": "(pieces, t) => 60 + 5 * sin(t)"`. A rejected expression is reported once as `exprError` in the reply. |
| `strips` | `{"strips": [{"origin": 12}, {"origin": 40}]}` | Per-strip settings (LED counts come from LED settings). |
| `play`, `timeScale` | `{"play": false}` | Pause, or slow motion / fast-forward. |
| `autoApply` | `{"autoApply": false}` | Stop forcing every segment onto the Held effect (to test wiring with stock effects). |
| `save`, `defaults`, `reset` | `{"save": true}` | Persist to `/held.json`, restore defaults, or restart the engine state. |

`GET /json/held` returns the state and the full config. `GET /json/held?s` returns the state only:

```json
{"v":1,"playing":true,"level":0.4,"mask":3,"count":2,"numPieces":6,"active":true,
 "events":[{"t":"pieceIn","age":0.8,"dur":3}], "params":{...}, "strips":[{...,"start":0}]}
```

## Audio link

The audio "brain" ESP32 (repo `held-electronics`) reads the six pocket sensors and plays the heartbeat and stories. It reports what's happening as plain-text lines over a serial link, following `held-electronics/docs/Held_Lighting_Serial_Messages.md`. The lighting controller reads them on UART1.

| Audio brain | Lighting controller | Purpose |
|---|---|---|
| GPIO4 (UART1 TX) | **GPIO32** (`HELD_LINK_RX`) | Messages from the brain |
| GPIO18 (UART1 RX) | **GPIO33** (`HELD_LINK_TX`) | Replies (`PONG`, `HELLO`, `LOG …`); optional |
| GND | GND | Required |

Both boards use 3.3 V logic, so they connect directly. The link defaults to 115200 baud, 8N1. GPIO 32/33 are free on both an ESP32 DevKit and a TinyPICO, and avoid the PSRAM pins of WROVER/PICO modules.

The pins and baud rate can be changed at runtime in **Strip config → Hardware: audio link**. They are saved on the device in `/held_hw.json`. Over the API, send `{"hw": {"linkRx": 25, "linkTx": 33, "linkBaud": 115200}}`; `-1` disables a pin. The build flags `HELD_LINK_RX` / `HELD_LINK_TX` / `HELD_LINK_BAUD` are only the first-boot defaults.

If a pin is in use (e.g. by an LED output), the link stays off and reports why in the link status. It retries every 5 s, so moving the LEDs off that pin brings the link up.

| Message from the brain | What the lights do |
|---|---|
| `BEAT <n> <bpm> <dub ms> <next ms>` | The heartbeat emits one pulse per `BEAT`, placed so the lub peak lights the origin as the lub sounds. The heartbeat's own BPM is ignored while beats arrive. If none arrives for `beatTimeout` seconds (default 4), the heartbeat goes back to its own BPM. Gaps in `n` are counted as missed beats. |
| `COUNT <seated> <required>` | Sets the piece count, which drives the level and the piece in/out events. `required` becomes the number of pieces. The first `COUNT` after the lights start is adopted silently, so a lighting reboot doesn't replay a "piece in". |
| `STORY START <k>` | Plays the last-piece animation, if **Last-piece animation starts on** is set to "Story start". Not sent by the brain yet; see below. |
| `STORY END <k>` | Plays the **Story ended** event: a warm glow that spreads from the origin and fades. |
| `PING` | Answered with `PONG`. |
| anything else | Ignored (counted as "lines ignored"). |

At startup the lights send `HELLO` and `LOG Held lighting ready`. They send `LOG lights: …` when they start or stop following `BEAT`.

The settings are under **Setup → Audio link**:

- **Last-piece animation starts on:** "Last piece" or "Story start".
- **Follow audio heartbeat** (`beatSync`).
- **Beat timeout.**

On a device, the same section shows the link status. Lines typed there are handled as if they came from the brain, and the quick buttons send sample `BEAT`, `COUNT` and `STORY` lines, so the lights can be tested without the brain. Over the API, `GET /json/held` includes a `link` object (counters, last line, last `BEAT`, seated/required, story).

## Hardware configuration

On a device, **Strip config → Hardware** sets the LED outputs and the audio link pins, without rebuilding the firmware.

- **LED outputs.** This is WLED's own LED configuration in a simpler form. For each output you set:
  - the strip type, from the digital types this build supports (for example WS281x, SK6812 RGBW, TM1814, APA102, WS2801);
  - the data pin, plus a clock pin for 4-wire types;
  - the LED count, color order, and whether it is reversed.

  **Apply LED outputs** reads the current hardware section of `/json/cfg`, replaces the output list, and posts the whole section back. WLED then rebuilds the outputs live and saves `cfg.json`, keeping everything else (power limit, timing, buttons). Up to 4 outputs; each becomes one Held strip. Settings not offered here are still under **All LED settings** (`/settings/leds`).
- **Pin pickers** come from `/json/pins`:
  - they mark pins that are already in use (LEDs, the audio link, system), as well as boot/strapping pins;
  - input-only pins are left out for outputs;
  - the UI refuses a pin used twice, and warns when an LED pin is also the audio link's.
- **Audio link:** RX pin, TX pin and baud rate; see [Audio link](#audio-link).

The direct piece-sensor pins (`HELD_SENSOR_PINS`, below) are still a build-time setting.

### Answers to the open questions in the proposal

- **WLED or custom firmware?** Custom: WLED is the base for WiFi, LED setup and the web UI, but the Held engine and this protocol are our own code. The messages are used as proposed; no JSON is needed.
- **UART and pins:** UART1 on the lighting ESP32, RX GPIO32 and TX GPIO33, as above.
- **115200 baud:** yes.
- **Replies:** `PONG` for `PING`, `HELLO` at startup, and occasional `LOG …` lines, which are fine to echo into the brain's Serial Monitor. Nothing needs an answer.
- **`STORY START <k>`: yes please.** At the moment the last-piece animation starts when `COUNT` reaches `required`. Someone pulling a piece and re-seating it mid-story would then replay it while the audio carries on. With `STORY START`, set the trigger to "Story start" and the lights follow the audio exactly.
- **`TARGET`:** not needed. `BEAT` carries the rate, and our transitions follow the piece count.
- **One addition:** if the brain answered `HELLO` by re-sending `COUNT`, the lights would resync after a lighting reboot without waiting for the next piece change.

### Piece sensors on the lighting board

`wled00/held/held_input.cpp` can read hall sensors wired straight to the lighting controller, for a standalone setup without the brain. Add the GPIOs to the build flags, one per piece:

```ini
build_flags = ... -D HELD_SENSOR_PINS=25,26,27,14,4,13   ; active-low with pull-up
              ; -D HELD_SENSOR_ACTIVE_HIGH                ; if the sensors drive high
```

The pins are debounced (30 ms) and only edges are reported, so pieces set from the UI stay set until a sensor actually changes.

### Adding a layer or a parameter

The engine exists twice: C++ for the controller and JS for the simulator. They are kept identical on purpose, and the tests enforce it.

1. Add the parameter to `schema.js` **and** `held_params.h`, in the same position. `npm test` fails if keys, order, types, limits or defaults differ.
2. Implement the behaviour in `held_core.cpp` and mirror it operation-for-operation in `engine.js`. Keep random draws (`rand01()` / `_rand()`) in the same order. In C++, draw into separate statements, because argument evaluation order is unspecified.
3. A new layer also needs:
   - a group in `GROUPS` and a namespace in `held_core.h`,
   - an entry in `HELD_SCHEMA.layers`,
   - a `tick…`/`render…` pair in both engines.
   
   For an event, also add it to `EV_TYPES` / `EVENT_NAMES`, and make `enabled` its first parameter.
4. Run `npm test`. It includes the native parity check, which is skipped if no host C++ compiler (g++, clang++ or MSVC) is found. Then run `pio run -e held_esp32`.

## Notes and deliberate choices

- **Heartbeat speed defaults are 14 → 22 LED/s** rather than the 5 → 10 first specified. Successive beats are `speed × 60 / BPM` LEDs apart. At 5 LED/s and 45 BPM that is 6.7 LEDs, less than the 10-LED waveform, so the beats overlap into a uniform texture. Keep `speed × 60 / BPM` above `pulseWidth` for distinct beats.
- **Strip size vs. the heart.** 120 LEDs at 60 LED/m is a 2 m loop, which doesn't fit inside the heart. On the middle front/back plane the inside is only about 36 cm wide. The 3D view shows the real heart model at true scale. Use the strip's **Aspect** and **offset** settings to shape and place the loop. About 84 LEDs at 60/m (aspect 1.55, side −30 mm, height −40 mm) fits.
- **The 3D heart needs internet.** three.js (about 170 KB gzipped) is too big to serve from the ESP32, and on the controller's access point phones have no internet. So the page starts with a small canvas-2D view, showing the heart's bounding ellipsoid. If three.js can be loaded from the CDN, it switches to a WebGL view of the translucent heart model, lit from inside by the LEDs. Add `?lite` to the address to stay on the canvas view.
- **WLED features compiled out:** Alexa, Hue sync, PixelForge, particle-system effects, and usermods. Network realtime protocols (E1.31/Art-Net/DDP) are still compiled in. They are inert unless something sends to them, and removing them touches a lot of WLED; disable them later if flash gets tight (currently ~81% of the app partition).
